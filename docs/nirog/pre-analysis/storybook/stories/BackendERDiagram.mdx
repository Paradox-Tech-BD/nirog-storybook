# Latest Backend ER Diagram

This is the logical database relationship model for the current backend baseline. It deliberately separates three concepts that often become incorrectly merged: the shared catalog product, machine-extracted prescription evidence, and the profile-private regimen that the user has explicitly confirmed.

<MermaidDiagram title="Nirog logical backend ER diagram" chart={backendER} />

## Relationship interpretation

An `ACCOUNT` receives authority through a time-bounded `PROFILE_MEMBERSHIP`; the `PROFILE` is the patient/dependent data boundary. A `PRESCRIPTION_DOCUMENT` can have several immutable pages and several scan attempts. A scan yields extracted evidence and candidate product matches. A `REVIEW_DECISION` may create one profile-private `REGIMEN_ITEM`; it does not mutate the published catalog.

Every regimen has versioned instructions and append-only dose events. Catalog products remain attached to a `CATALOG_RELEASE`, while unresolved medication names remain private to the profile. `AUDIT_EVENT` records the acting account and outcome without becoming a copy of the health-data resource.

## Critical constraints

The database prevents repeated offline writes with a unique device/client-command key. A review decision is unique for its extracted line, evidence version, and idempotency scope. Regimen versions increase monotonically per regimen item. Published catalog and match-index releases are immutable; corrections create a new release. Audit events are insert-only for application principals.
