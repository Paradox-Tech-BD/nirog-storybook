# Browser Push Foundation Progress

## Scope and implemented boundary

Nirog has implemented the **browser Web Push registration foundation**, not a push-delivery feature. Core revision `441c06f` introduced the authenticated capability contract and encrypted registration boundary. Web revision `99d025b` introduced a deliberate opt-in card, minimal service worker, installable manifest, same-origin proxy allow-list, VAPID decoding, and self-only registration/revocation requests. The deployed implementation has **no push sender, provider credential, private VAPID key, FCM configuration, provider payload, or push-delivery claim**.

The authenticated Core capability route, `GET /api/v1/delivery-registrations/web-push/config`, discloses a public VAPID key only when encrypted registration persistence and the public key are both configured. It never returns the registration-encryption key, a VAPID private key, a provider credential, a browser target, ciphertext, or a registration identifier. The registration command accepts browser endpoint and key material only through the existing encrypted Core persistence boundary; the Web companion never renders those values back to the user.

> **Delivery terminology:** a saved registration enables a future sender to target an opted-in browser. It does not mean that any notification was sent, delivered, displayed, read, or acted upon.

## Runtime capability activation

The targeted Railway service `@nirog/api` is online with the required API-only registration encryption prerequisite and public VAPID configuration present. A temporary safe startup diagnostic confirmed only the two prerequisite booleans, then was removed from active Core source. The cleanup revision `62db1aa` completed successfully on the targeted API service. The unrelated Railway service named `nirog-core` was not approved or changed.

The Vercel connector was used to verify the Nirog Web production project and its deployment. Its runtime observation confirmed that the Web server reaches the active `@nirog/api` host and receives HTTP `200` for the capability request. The response follows the standard Core success envelope: the active result appears within `data`, where capability is available and a public VAPID key is present. A top-level-only inspection therefore appeared unavailable even though the actual typed client path was correctly enabled. The temporary Web proxy diagnostic used to establish that fact was removed in cleanup revision `829da3f`, which is deployed to production.

The notification-policy workspace now correctly renders **Set up browser push** only after the capability response is available. Permission is requested only from that user-initiated action; loading the page does not trigger a permission prompt.

## Controlled browser test outcome

One controlled opt-in attempt was made from an authenticated owner session. The service worker registered successfully, but the automated browser remained at the browser-native notification state `default` / `prompt` and did not surface a grantable permission dialog. It created **no PushSubscription**, submitted **no encrypted Core registration**, and therefore had no registration to revoke. No external notification was sent and no provider configuration was added.

This is a browser-automation limitation, not proof that the registration lifecycle has failed. Increment 7 remains open until a person uses a real device or a browser session where the native notification permission can be granted, completes one registration, and immediately revokes it through the same self-only UI. The follow-up must verify only safe lifecycle state: that the UI reflects a local registration, then returns to the unregistered state after revocation and local unsubscribe. It must not inspect or publish endpoint material, subscription keys, target values, recipient details, or credentials.

## Verification and quality record

Core `pnpm verify` passed after the diagnostics were removed: **41 test files passed**, **1 file skipped**, **117 tests passed**, and **9 expected skips**. The expected OCR fixture console noise remains unrelated to browser push. Web verification also passed after cleanup: **12 test files and 23 tests**, ESLint, and a production Next.js build under `NODE_ENV=production`.

The temporary capability diagnostics were introduced only to distinguish three non-sensitive conditions: whether the active API process saw its prerequisites, whether the Web proxy targeted that active API host, and whether the capability data was inside the usual success envelope. Once each condition was confirmed, both diagnostics were removed and their cleanup deployments completed.

## Required manual completion protocol

From an authenticated owner browser where the native notification prompt can be granted, open **Notification policies** and select **Set up browser push**. Grant permission at the browser prompt, wait for the page to report a registration-safe status without target data, then use the page’s self-only revoke control immediately. Confirm that the local subscription is absent and the page returns to its unregistered presentation.

The test must stop there. It must not enable a sender, add FCM, configure a VAPID private key, send a test notification, expose a provider target, create a clinical notification, or imply real-world delivery. After that registration-and-revocation proof succeeds, the increment can be marked complete and the next delivery increment may assess external email activation prerequisites separately.
