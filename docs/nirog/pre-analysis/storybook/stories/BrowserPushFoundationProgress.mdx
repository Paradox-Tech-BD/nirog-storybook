# Browser Push Foundation Progress

## Implemented source boundary

The browser-push foundation is implemented and published in Core revision `441c06f` and Web revision `99d025b`. It adds an explicit browser-controlled opt-in surface, a minimal service worker, an installable Web manifest, safe same-origin proxy paths, and encrypted Core registration synchronization/revocation integration. It still has **no push sender, no provider credential, no private VAPID material, and no push delivery claim**.

Core adds the authenticated `GET /api/v1/delivery-registrations/web-push/config` capability contract. It returns a public VAPID key only when both encrypted registration persistence and a public VAPID key are configured. It never exposes the registration encryption key, a private VAPID key, provider sender credentials, targets, ciphertext, or registration identifiers through the capability response.

| Layer | Implemented behavior | Explicit safety boundary |
| --- | --- | --- |
| Browser UI | Requests permission only after a person selects **Set up browser push** | No automatic prompt; no permission request when capability is unavailable |
| Service worker | Handles a future push event with a generic Nirog notification and opens the care plan on click | Does not parse, store, or display clinical payload content |
| Registration command | Submits endpoint and `p256dh`/`auth` material to the existing encrypted Core registration API | Browser target/key material is never rendered back into Web |
| Revocation | Calls the idempotent self-registration DELETE route, then unsubscribes the local browser subscription | Revocation is not a claim that a provider message was cancelled |
| Capability gate | Requires both Core encryption-key availability and a public VAPID key | No sender, send adapter, FCM credential, or external delivery |
