# Data Change and Migration Governance

Schema, policy, model, catalog, retention, and backfill changes can alter user-visible meaning or historical explanation. Nirog uses an expand–migrate–contract sequence: additive structures first, compatible readers/writers, bounded idempotent backfill, validation/reconciliation, controlled activation, observation, and only then removal of old paths.

<MermaidDiagram title="Safe data-change lifecycle" chart={migrationFlow} />

Migration evidence includes owner, compatibility contract, backfill checkpoint and counts, constraint/reconciliation result, rollout version, metrics, and rollback/compensation decision. Direct SQL repair of clinical-management history is not an acceptable rollback pattern; a corrective version/action preserves explainability.
