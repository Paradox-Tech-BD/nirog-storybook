# User Modules, API Semantics, and Rate Limits

The user slice no longer uses one broad application service or one combined route file. It is split into focused application **queries**, **commands**, authorization support, typed errors, feature-local HTTP contracts, response mappers, four route modules, and a small feature registration module.

<MermaidDiagram title="Feature-local Clean Architecture flow" chart={featureLayout} />

## One response vocabulary

All successful business responses use:

```json
{ "data": {}, "meta": { "correlationId": "request-uuid" } }
```

All failures are `application/problem+json` with `type`, `title`, `status`, `code`, and `correlationId`. Validation, authentication, authorization, not-found, idempotency, rate-limit, unknown-route, and unexpected errors all go through the same global mapper. `X-Correlation-Id` is emitted on every response.

## Scalar and generated OpenAPI

Scalar is live at **`/reference/`**, backed by generated OpenAPI at **`/openapi.json`**. Feature-local TypeBox contracts provide the generated request schemas, success-envelope responses, shared problem schemas, bearer security metadata, and rate-limit `429` responses. `pnpm openapi:write` commits the same generated contract as `openapi/nirog-core.openapi.json`.

## Account-aware limits

The rate-limit hook executes after Clerk authentication. Authenticated traffic is keyed by **local Nirog account ID**, so every device for one account shares one quota. Anonymous traffic is keyed by client IP. Health, OpenAPI, and Scalar are public exemptions.

For isolated tests the plugin uses its in-memory store. Local Compose includes Valkey and points the API to `redis://valkey:6379`. Production startup rejects a missing `RATE_LIMIT_REDIS_URL`, preventing silently per-instance limits in an autoscaled environment. The rate-limit response uses the same problem shape with `429 RATE_LIMIT_EXCEEDED` and standard rate-limit headers.
