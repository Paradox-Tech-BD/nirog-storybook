# Bounded Strapi Decision

Nirog adopts a **bounded Strapi topology**. The clinical system of record is **Nirog Core**: a TypeScript modular monolith using Node 24, Fastify, TypeBox, Drizzle, PostgreSQL, explicit RLS, and Scalar. Strapi is a separate workforce administration plane, not the patient-data backend.

<MermaidDiagram title="Nirog Core, bounded Strapi, and worker topology" chart={topology} />

## Why this boundary is deliberate

**Nirog Core owns clinical authority.** It is the only service that provides Flutter APIs, evaluates patient profile capability, applies consent and resource checks, writes clinical tables, emits audit/outbox records, and serves Scalar/OpenAPI contracts.

**Strapi earns a narrow role.** A pinned Strapi project can accelerate workforce catalog drafting, controlled knowledge authoring, editorial templates, and optional administration tooling. It has its own database, workforce identity provider, storage boundary, upgrade lifecycle, and custom plugin surface.

**No shared clinical database.** Strapi cannot read or write patient records. A reviewed catalog release crosses the boundary as a signed, versioned handoff command; Core validates it and writes an immutable catalog release itself.

**Python remains a worker runtime.** OCR, embedding, and retrieval workers receive only minimum-necessary event envelopes through explicitly registered PostgreSQL outbox handlers, then return evidence or retrieval results through restricted Core commands. They cannot activate a regimen or create adherence state.
