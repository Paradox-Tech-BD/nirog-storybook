# Clerk User Subsystem: Verified API and Authorization Slice

Nirog Core now has a **verified first implementation slice** for Clerk-authenticated users. Clerk proves the external principal; Core performs local account mapping, profile scope, permission evaluation, RLS context, idempotency, audit/outbox work, and the generated API contract. The verifier is a root Fastify pre-handler, which avoids plugin encapsulation excluding user routes.

<MermaidDiagram title="Authenticated request path" chart={requestPath} />

## What is now delivered

The modular workspace includes `@nirog/auth`, `@nirog/user-domain`, expanded `@nirog/access`, and Drizzle-backed user repositories. Migration `0001_clerk_user_subsystem.sql` adds the identity, profile-access, team, invitation, consent, device, and provider-event records, RLS policies, and the restricted `ensure_clerk_account()` JIT projection function.

The API exposes Clerk-protected current-account, preferences, patient-profile, profile-grant, team-creation, direct team-invitation, device registration/revocation, and consent create/withdraw routes. Every mutation is idempotency-key protected. Device fingerprints and optional push tokens are SHA-256 hashed before persistence and excluded from responses, audit metadata, and outbox payloads. Generated OpenAPI declares `/api/v1` as the server URL, and uses server-relative paths such as `/me`; Scalar is served at `/reference`.

<MermaidDiagram title="Persisted profile-grant authorization" chart={authorizationPath} />

## Access invariant

Profile ownership is implicit. Delegated access derives only from an active, persisted permission snapshot. Role templates are expanded when a grant is created, and authorization evaluates the stored snapshot rather than a mutable role label. The `PolicyEvaluator` interface retains the required future PBAC extension seam.

Team collaboration remains deliberately non-clinical: team membership **never** grants access to patient data.

The test matrix confirms anonymous rejection, dependency-injected verified principal flow, idempotency enforcement, generated bearer security metadata, fail-closed Clerk configuration, persisted permission decisions, revoked-grant denial, native request-transaction context behavior, direct invitation owner/admin/recipient boundaries, account-self device control, profile-owner consent writes, no patient-profile visibility through team membership, and the forward RLS policy corrections. Railway completed the migrator revision before activating the matching API revision; public liveness returned HTTP `200`.

## Deliberately pending endpoints

The signed Clerk/Svix receiving endpoint is activated in the Nirog Development instance and was verified with a real `user.created` delivery acknowledged by Core with HTTP `202`. Directed team invitations are deployed: owners may invite `admin` or `member`, team administrators may invite/cancel `member` only, and the intended local account alone can accept or decline. Device and consent lifecycle routes are deployed: account-self device registration/revocation is separate from profile-owner consent management; consent accepts only `data-sharing`, `research`, or `marketing` and creates no patient-data capability by itself. The remaining user-subsystem boundary includes lifecycle consumers for webhook outbox events and continued PostgreSQL integration coverage as further identity policy slices are added.
