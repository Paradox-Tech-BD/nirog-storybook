# Isolated ML Worker

The ML worker is a **separately deployed Python/FastAPI service** that performs OCR and structured medication-candidate extraction. It is deliberately isolated from clinical storage and public identity systems. The worker is an evidence processor, not a clinical authority.

<MermaidDiagram title="Minimum-authority ML worker interaction" chart={workerFlow} />

## Minimum-authority design

The worker accepts a single authenticated internal event shape: the OCR event type, correlation reference, profile reference, evidence reference, and job reference. It does not receive a database connection, a broad object-store credential, Clerk credentials, or permission to create a regimen.

Its dedicated Core client can do only three categories of work: request a job lease, request evidence access for that active lease, and submit the result for that lease. Each Core call uses the worker-only service identity. A missing or stale job resolves to a harmless no-op rather than a blind retry or cross-profile lookup.

## Lease-bound evidence access

Core authorizes evidence reads only after a worker holds a valid lease. The worker receives a short-lived evidence capability, streams the object, and enforces a configured maximum download size. Missing evidence and oversized evidence are permanent-access failures; object-store server failures and network errors are retryable-access failures.

The worker must not retain the evidence beyond the extraction operation. It must not write the object to an alternate store, include it in logs, or attach it to an outbox event.

## Extraction contract

The worker uses a local OCR/normalization pipeline and an external Gemini extraction provider to produce bounded structured candidates. Provider output is requested in JSON mode and is validated locally before Core receives it. Gemini supports schema-constrained JSON responses for predictable, type-safe extraction, but the product still treats provider output as untrusted until local and Core-contract validation succeeds.[1]

The provider boundary accepts supported image MIME types and uses a prompt-before-image request order. The worker never treats image support as a guarantee of clinical correctness; every result still passes the Nirog bounded candidate and confidence contract.[2]

The configured provider model is runtime configuration rather than an architectural trust boundary. Product behavior must depend on the persisted candidate contract and confidence policy, not on a provider-specific free-text format.

## Deadline and failure classification

Provider requests have a bounded timeout. A temporary provider, network, or evidence-access condition is reported to Core as a retryable OCR failure. A permanently unsafe or invalid extraction condition is reported as a permanent OCR failure. Core owns the resulting state transition, delay schedule, attempt budget, audit record, and outbox emission.

This division avoids stranded work. A bounded timeout becomes an explicit result callback instead of an indefinitely leased job. If a process ends before it can report a callback, the dispatcher’s expired-lease recovery sweep can safely schedule a new attempt or finish at the configured terminal boundary.

## What success does and does not mean

Worker success means Core has received a valid extraction result for an active lease. It does not mean a regimen exists. Core may persist extraction provenance and editable medication drafts; only a later explicit, authorized regimen command creates clinical regimen state.

### Verified provider-fallback acceptance

On 23 August 2026, a single user-authorized production evidence upload exercised the full isolated-worker path. The primary Gemini attempt returned a retryable provider quota response. The worker then performed its configured **bounded fallback** within the active lease; Core accepted the result callback, persisted a processed evidence state, one extraction with seven aggregate candidates, and seven editable drafts. All seven drafts remained in the correction-required state, and zero drafts were submitted.

This result verifies that a provider quota response does not inherently become a terminal rejected evidence record when the bounded fallback can complete. It does **not** remove the provider dependency: when both bounded attempts remain unavailable, the worker returns only retry metadata and Core schedules the later of its policy delay or the provider hint. This bounded response follows the provider’s published guidance to retry transient `429` and `5xx` responses with backoff and a maximum retry limit.[3] The resulting delayed, identifier-only event remains owned by Core’s outbox policy. Documentation and UI must not describe a quota-limited run as successful unless persisted Core state confirms the processed extraction and draft aggregates.

No medication text, field values, model response, signed evidence capability, evidence identifier, or regimen action is recorded on this page. The verification did not invoke an explicit draft-submission or regimen command.

### Verified result-contract rejection repair

Later on 23 August 2026, one newly supplied owner-authorized JPEG was submitted exactly once through the same normal Web path. Its persisted aggregate outcome was terminal rejected evidence with zero extraction and zero drafts. Redacted worker diagnostics showed a retryable Gemini `503` followed by a Core result-callback `400`. This distinguishes the incident from a browser upload failure, evidence-storage authorization failure, dispatcher non-delivery, or a claim that the provider response itself was permanent.

The proven defect was at the private result boundary: the worker’s candidate serializer sent unread optional string and numeric fields as JSON `null`, whereas the Core TypeBox schema accepts those fields only when absent. Core commit `e50b4d3` now removes null-valued optional fields while retaining required schedule and interval values, and adds a synthetic payload regression test at the Core-client boundary. The complete isolated ML-worker suite passed 26 tests and the targeted Railway worker deployment reached success. The already terminal record was deliberately not manually requeued or resubmitted, so this repair is not documented as a new successful extraction. No image content, OCR output, medication field, draft edit, or regimen action was accessed or created.

The repair was subsequently confirmed through one new normal owner-initiated automatic run using the authorized JPEG. The aggregate persisted result was processed evidence, one extraction, and seven editable drafts. No result-callback `400` appeared in the active repaired worker runtime, and no medication, draft, or regimen command was issued by the verification. This confirms the callback-contract repair as functional in the deployed asynchronous path while leaving all clinical confirmation explicit and separate.

### Aggregate multi-file confirmation

Three further user-authorized image workflows then completed through the normal owner file-picker, Core outbox, isolated-worker, and draft-persistence path. Each reached processed evidence with one extraction. Their editable-draft aggregates were seven, five, and ten respectively. The verification did not inspect, transcribe, or document image contents, candidate fields, medication values, or evidence identifiers.

One separately authorized test regimen was later created only through the explicit draft-correction, regimen-create, and draft-submission sequence. That downstream care-plan test validates the Core and dispatcher reminder lifecycle; it does not give the ML worker authority over reminders, doses, inventory, refills, notifications, or regimen activation.
