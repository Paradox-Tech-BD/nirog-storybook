# Web Companion

The Web companion is a **Next.js patient and caregiver experience**, not a second clinical backend. It renders user-facing workflows and mediates browser requests through a server-side Core bridge. This avoids granting the browser unrestricted Core access while preserving a responsive, session-aware user experience.

<MermaidDiagram title="Web companion to Core authorization boundary" chart={webBoundary} />

## Server-side Core bridge

The browser calls same-origin Web routes. The Web server validates the Clerk session, obtains a session token only for the active request, forwards only allowed headers, and proxies only allowlisted Core paths. It preserves Core’s typed success response or problem response and propagates a correlation identifier when Core supplies one.

This boundary is intentional. The browser is not asked to construct arbitrary Core calls, and the Web server does not become a permissive relay. An unauthenticated session receives an authentication problem response; an unconfigured Core target receives a configuration problem response; a missing token receives a token-unavailable response; and a network failure becomes a bounded Core-unreachable response.

## Evidence workspace responsibility

The prescription-evidence workspace lets a signed-in user select a profile and prescription, choose an allowed file, authorize a time-limited upload, upload the bytes, and complete the evidence record. Only after the completion command does Core queue automatic OCR work.

The interface distinguishes the user-visible stages of **authorization**, **transfer**, **queueing**, and **completion**. Client-side validation checks the permitted file type and size before initiating the workflow. A failed upload does not silently create a completed evidence record, and a failed UI attempt is not described as a clinical change.

The file chooser is a native, labelled browser control rather than a hidden-input-only interaction. This preserves the same protected upload sequence while improving keyboard, assistive-technology, and browser-automation access. Selecting a file validates it locally; the separate “Start automatic extraction” action is the only browser action that authorizes the normal evidence-upload and OCR-queue sequence.

### Verified automatic-draft acceptance

On 23 August 2026, one user-authorized production upload completed through the normal signed-in workspace. Aggregate persisted state transitioned to processed evidence with one extraction, seven candidates, and seven editable correction-required drafts. The browser rendered the persisted processing and draft state only after Core recorded it; it did not infer success from the upload acknowledgement.

The worker encountered a retryable primary-provider quota response and completed through its configured bounded fallback. This validates the Web path as a consumer of Core-authoritative state, not a provider-status simulator. It does not imply that provider availability is unlimited; a later quota-limited run must remain visibly deferred or retryable until Core records a terminal or successful outcome.

No medication field value is documented here. No editable-draft field was changed, no “Confirm and save medication regimen” action was invoked, and the submitted-draft aggregate remained zero. The result therefore verifies automatic ingestion and draft creation, not regimen creation or clinical confirmation.

## Stable clinical read model

The workspace performs a stable, explicit Core-read bootstrap instead of recursively recreating its own loader from React state updates. It reads the account/profile projection, prescription list, evidence metadata, extraction metadata, medication drafts, and permitted care-circle summary through the server bridge. Independent downstream reads are allowed to resolve separately, so a partial status failure does not erase the whole workspace or leave the user facing an unexplained blank screen.

The UI shows a deliberate **refreshing** state while this profile-scoped sequence completes, then changes to a live record state. A person can refresh manually and receive a safe error message. The browser does not infer successful extraction from an upload acknowledgement, worker request, or spinner; it waits for persisted Core state.

This distinction matters in terminal states. A received evidence file with a rejected processing outcome is rendered as a visible status with no extraction and no draft. It is not presented as a completed prescription, and the interface does not invite the user to bypass the backend’s retry or attempt policy by manually creating hidden workflow data.

## Care-circle access experience

The authenticated Web navigation includes a separate **Care circle** destination. It shows the signed-in actor’s own relationship to the selected profile, rather than treating a caregiver roster as generally readable account data. Core returns an owner-or-grant access designation and, for an active grant, the caller’s own role and permission snapshot. The page intentionally excludes joined names, emails, avatars, and other members’ permission sets.

This solves a practical default-caregiver boundary. A caregiver with `profile.read` can discover an active delegated profile and see their own access context. The complete grant roster remains a manager-only capability protected by `share.manage`; its failure is not used to hide the caregiver’s own authorized care workspace. Neither page grants `regimen.write`, changes a relationship, or blocks automatic extraction.

### Live delegated-caregiver verification

On 23 August 2026, a dedicated development-only identity received one owner-created, time-bounded `caregiver` grant and exercised the production Web path. Core returned the recipient’s own `grant` access kind, `caregiver` role, and eight-permission snapshot. The snapshot included the configured profile, evidence-metadata/evidence-image, and regimen-read capabilities; it excluded **`regimen.write`** and **`share.manage`**. The live browser therefore confirmed that an authorized caregiver can inspect aggregate evidence, extraction, confidence, and draft status without becoming a routine extraction gate or care-circle manager.

The test exposed and then corrected a client-boundary defect. Before the repair, the browser rendered editable medication fields and regimen-confirmation controls despite the absence of `regimen.write`. The Core command boundary would still have rejected a mutation, but the interface was misleading and unnecessarily presented a clinical action. The repaired workspace reads the self-only Core access context before rendering actionable controls. A read-only caregiver now receives draft status and confidence summaries only: the deployed verification observed **seven** read-only summaries, **zero** editable clinical controls, **zero** regimen-submit controls, and no evidence-upload control. The workspace also skips the manager-only roster read for a caller without `share.manage`, preventing a false access-warning banner.

Temporary test cleanup also verified the narrow same-origin bridge. The proxy now allowlists the UUID-scoped profile-grant revocation endpoint and forwards `DELETE` using the active Clerk token. It preserves bodyless upstream responses such as Core’s `204` revocation success instead of incorrectly converting them to a gateway failure. The temporary grant was revoked, and the user-confirmed synthetic Clerk development identity was deleted. No clinical field, draft, evidence, or regimen was changed during this exercise.

## Confidence and correction experience

The UI presents the field-confidence threshold as **0.70**. A candidate with an eligible confidence can pre-populate a field, while a missing or lower-confidence field is visibly marked for correction. Medication name, dose, route, frequency, schedule times, and interval remain editable inputs.

This is assistance, not automation of treatment. The Web companion never treats a confidence score as consent, clinical validation, or authority to activate a regimen.

## Explicit regimen boundary

The visible “Save medication regimen” action is deliberately separate from OCR. The user confirms or corrects the editable draft first. The Web companion then sends the ordered explicit commands to update the draft, create the regimen, and mark the draft submitted. Core re-evaluates authorization and validation for every command.

> Uploading evidence, completing OCR, or seeing a high-confidence field must never create a regimen by itself.

Patients and authorized caregivers can submit only when Core grants the applicable write permission. Caregivers with inspection access may see provenance and draft state, but they do not routinely block automatic extraction. The browser must use the same Core permission snapshot to withhold mutation controls, while Core remains the authoritative enforcement point for every command.

## Error-handling expectations

The Web companion uses problem responses for authentication, configuration, token, and Core-reachability failures. It uses per-action UI state for upload and draft-submission failures, and it reports that a failed submission did not create a regimen. UI errors are not a substitute for server-side authorization or idempotency.

The Web companion also treats an unavailable manager-only grant roster as a bounded partial-read outcome. A default caregiver can still receive the self-only access context provided by Core. This prevents an access-governance permission from becoming an accidental prerequisite for ordinary profile visibility.
