# Detailed Worker Failure Recovery

This sequence diagram shows the end-to-end handling of a committed asynchronous effect—from the original FastAPI transaction to outbox publication, duplicate delivery, scoped execution, provider uncertainty, retries, and dead-letter recovery.

<MermaidDiagram title="Async worker sequence: committed event through safe recovery" chart={detailedWorkerRecovery} />

## How to read the diagram

The **outbox** separates durable domain commitment from later task delivery. Relay duplication is deliberately tolerated. The **consumer ledger** makes completed owned effects idempotent, while a re-read of current aggregate/stage state turns stale or cancelled work into a safe no-op.

Only temporary, still-relevant faults receive a bounded retry. Corrupt inputs, policy denials, revoked access, and incompatible event/configuration contracts end safely rather than loop. When an external provider response is lost after a request might have been accepted, the worker reconciles with the deterministic provider key before deciding whether another request is valid.

Dead-letter handling is an operator workflow: it classifies the event as requeue, cancel, supersede, manual resolution, or defect remediation, then creates a fresh attempt from authoritative state where appropriate. It never blindly republishes an old queue payload.
