# Deployment and Scaling Guide

Nirog deploys and scales workload classes separately without prematurely splitting the modular FastAPI backend into microservices. The API, outbox relay, ML workers, projections, notification dispatch, catalog/index jobs, and maintenance workers each receive independent identities, queue bindings, resource limits, health checks, monitoring, and scale signals.

<MermaidDiagram title="Workload units scale independently around one authoritative database" chart={scaleTopology} />

## Scaling posture

API replicas scale from request concurrency, latency, resource use, and database-pool wait time. Worker pools scale from queue age/depth, measured task duration, provider quota, cost/budget, and task-specific resource constraints. PostgreSQL connection budget is a hard cap on API scale-out; broker queue depth is never the only worker signal; and ML saturation triggers delayed/manual-entry behavior rather than blocking the core medication workflow.

## Safe operations

The guide defines isolated development/staging/production environments, environment-scoped secrets and identities, graceful worker draining, queue backpressure, expand/migrate/contract schema changes, canary releases, release-specific rollback, backups/PITR, restoration drills, and capacity review cadence. Derived queues, projections, and indexes can be rebuilt from PostgreSQL authoritative state after recovery.
