# Async Failure Handling and Security

This detailed review explains how Nirog turns its worker architecture into a safe operational lifecycle and how its authentication, authorization, data, process, storage, and audit controls compose into one security model.

<MermaidDiagram title="A durable worker lifecycle handles duplicate delivery and classified failure" chart={workerRecovery} />

## Failure handling in practice

The API commits business state, audit, idempotency outcome, and an outbox record together. Relays and brokers may deliver an event more than once, so each worker uses a consumer ledger and re-reads authoritative state before applying an owned effect. Transient failures receive bounded backoff; policy, input, stale-version, and deterministic configuration faults do not retry blindly. Dead-letter items are recovery decisions—not passive storage—and requeue from current state rather than stale payload.

Unknown external-provider outcomes receive special treatment: worker intent is durable, provider requests use deterministic idempotency keys, and reconciliation determines whether a request was accepted before any resend.

<MermaidDiagram title="Layered authentication and authorization controls" chart={layeredSecurity} />

## Security and authentication layers

OIDC establishes the account identity and produces an immutable backend `ActorContext`. A server-side profile policy then evaluates ownership, active caregiver grant, permission set, consent, time validity, and resource relation for every sensitive request. Repository scoping and PostgreSQL RLS add independent constraints, while worker identities, private evidence storage, purpose-bound capability URLs, secret management, network controls, and redacted audit logs reduce process and data exposure.

Neither an access token, a profile ID, a team membership, an object UUID, nor a queue message is authorization by itself. ML workers have only evidence-stage permissions and cannot write regimen, adherence, notification, or profile-access state.
